# Version Control and Collaboration

## Repository

The MSIT 5910 Capstone project is maintained in a GitHub repository named `technology-governance-capstone`. The repository contains the project artifacts developed throughout the Capstone, including assessment materials, design artifacts, documentation, and project-management materials.

Repository URL:

https://github.com/Analyst4life/technology-governance-capstone

## Repository Organization

The repository is organized into folders according to the type of project artifact:

- `assessment/` — Technology governance practices, organizational factors, assessment, scoring, feasibility, and roadmap materials.
- `design/` — Capstone architecture, process, module design, requirements, and other design artifacts.
- `documentation/` — Capstone written documentation, reports, requirements, and supporting documents.
- `project-management/` — Capstone project planning, progress tracking, milestones, and project-management materials.

This structure separates different types of project artifacts and makes them easier to locate and maintain.

## Branching Approach

The repository uses two branches: `main` and `development`.

The `development` branch is used for ongoing project work and changes to project artifacts. The `main` branch represents the stable version of the project. Changes are developed and committed on the `development` branch before they are considered ready for the stable version.

This approach provides a separation between work in progress and the stable project version. It also provides an opportunity to review changes before they are incorporated into `main`.

## Commits and Traceability

Project changes are recorded through Git commits. Commit messages describe the purpose of individual changes, such as adding the process architecture, module design, system requirements, or architecture diagram.

The commit history provides a record of how the project has developed over time. This supports traceability because changes to project artifacts can be associated with specific commits rather than relying only on the current version of a document.

For example, the design artifacts in the `design/` folder were added through separate commits. This makes it possible to identify when major design components were added and to review earlier versions when necessary.

## Documentation and Consistency

Version control helps maintain consistency among the Capstone's project artifacts by keeping the files and their changes within the same repository. As the project develops, updates to requirements, architecture, module design, assessment materials, and other documentation can be recorded through commits.

The repository therefore serves as both a central location for project artifacts and a history of changes made during the Capstone project.

## Collaboration

Although the Capstone is an individual project, the repository supports collaboration by providing a consistent location from which project artifacts can be reviewed. The repository can be shared with the instructor or other authorized reviewers so that the project files, organization, branches, and commit history can be examined.

The same structure could support collaboration if additional contributors were involved by allowing project changes to be maintained and tracked through branches and commits.
